# Council plugin: several local agents working one task together (proposal)

Status: proposal, not started. Research: a code survey of NetPI's extension points and a prior-art review
(AutoGen/AG2 group chat, Magentic-One, CrewAI, LangGraph, MetaGPT, ChatDev, CAMEL, OpenAI Swarm/Agents SDK, Anthropic's
multi-agent research system, multi-agent debate and its critiques, LLM blackboard systems, Google A2A, Claude Code agent
teams).

## What the prior art says

- Free-form group chat (AutoGen style) is where the failures cluster: chatter, ping-pong, everyone agreeing, a transcript
  that grows by members × turns, and an extra LLM call per turn to pick the next speaker. Every system that works adds
  hard turn caps and an explicit "done" signal.
- Coordination that needs no model call is the cheapest and the most robust on small models: a shared task board with
  atomic claims (Claude Code agent teams, blackboard papers), typed messages that roles subscribe to (MetaGPT), handoff
  tool calls (Swarm).
- State belongs outside the chat (Magentic-One's ledgers, Anthropic's plan in memory, MetaGPT's artifacts); messages carry
  references and a 1–3 line summary.
- Debate helps only on checkable steps and rarely beats sampling + voting at equal compute; copies of one model agree on
  the same mistakes. Use it as a module ("decide"/"review" items with blind first answers), not as the system.
- With 2–4 GPU slots a council of 4 is mostly queued turns, not parallel ones; keep every member's prompt short and its
  prefix stable (KV-cache reuse).

## Design

A board-first council with a light chair role; discussion lives in per-task threads, not one global chat.

- **Plugin** `plugins/NetPI.Council`, all policy in it; no host change. State in `ctx.Data` (the bus is best effort and
  only says "re-read"): `councils`, `inbox`, `tasks {id, title, goal, acceptance, deps, owner, leaseUntil, state,
  budget, parent}`, `messages {seq, council, task?, from, to?, kind, body, refs}`, member cursors. Claims are
  `ctx.Data.Transaction` compare-and-set with a lease (pattern: `ScheduleStore.ClaimDue`).
- **One inbox**: `council.post { councilId, text, source, key? }` (idempotent on `key`) is the single channel: the
  user, the chair, webhooks and schedules all post there; external payloads are stored and marked as data, not
  instructions. Webhooks/Schedules today only start their own chats: the first version adds a council-owned HTTP route
  (`ctx.Http`) and an own timer; routing the existing Webhooks/Schedules plugins into it later needs a small contract
  (an inbox-target service in `NetPI.Contracts`, all consumers updated).
- **Members** are long-lived chat sessions (`meta.council = { id, role }`, found via `SessionQuery.AttachedKey`), bound to
  the configured agents (`agents.use`), `meta.priority` low/normal so the user's chats come first, `meta.maxTurns`,
  `ask_user`/`agent_spawn` switched off (`meta.toolsOff`); the role text comes from a prompt section. Writing members get
  isolated worktrees (`workspaces.create` → `integrate` → `workspace retire`).
- **Tools** (Category `council`): `council_read` (digest since the member's cursor: its tasks, threads addressed to it,
  a one-line-per-task board), `council_post { task?, to?, kind, body }`, `council_task { action: add|claim|progress|done|
  blocked|release, … }`. Every member turn ends with one typed action; `pass` is free; pleasantries are refused.
- **Wake-up, pull not push**: the plugin wakes an idle member with a short `SendAsync` notice ("3 new items for you —
  call council_read"), debounced, derived from stored cursors and swept periodically (lost events cannot lose work).
  Members never wait inside a run (a waiting run holds a slot and the reload gate): they end the turn and are woken.
- **Chair**: one member (or a rule for simple sources) triages the inbox into tasks, merges duplicates, sets budgets,
  and closes the input when the acceptance checks pass. "Done" is the acceptance check (a test, a schema, or a second
  member's yes/no review), never "everyone agrees".
- **Decide/review items**: blind independent answers, at most one critique round with a required "strongest
  objection" field, then a vote or the chair's decision with the dissent kept.
- **Guards**: per task max turns/retries/wall time; per input max tasks and depth; council-wide message and turn caps,
  a stall counter (no board change for K turns, a task bouncing between members) that escalates to the chair, a pause
  switch, and `IAgentCallObserver` accounting (local models cost no money, so turns/tokens are the budget).
- **UI**: a Council tab (inbox, board, threads, members and their state) on `council.*` RPCs and a `council.changed`
  "re-read" event; member sessions grouped under their council instead of cluttering the chat list.

## Risks found in the code

- Slots: a run holds its slot for the whole run; 4 members on a 2-slot model queue by priority/FIFO (no deadlock as
  long as runs end). Members at low/normal priority, the user's chats above them.
- Reload gate: every run holds it; a council that is never idle would postpone plugin reloads indefinitely — batch work
  into discrete runs with idle gaps, and the pause switch.
- Sibling agents cannot message each other with the stock `agent` tool (subtree-scoped); the council's own tools are the
  channel. Chat-kind agents are all named "main": senders are named in the message body.
- Compaction of long-lived members costs a slot on a busy local model; pull digests keep transcripts short so it rarely
  fires.

## Build order

1. Inbox, board, claims with leases, cursors, wake-up, guards; one worker role; Council tab read-only.
2. Typed actions with constrained output; the acceptance/verifier step.
3. The chair (triage, planning, stall escalation); council HTTP route and timer as inputs.
4. Decide/review items (blind answers + vote).
5. Measure against one agent doing the same task (with self-consistency); keep the council where it wins.

Open questions for the owner: one council or several (per project)? Do members share one checkout or each get a
worktree per task? May the council start runs on paid agents, or only on local ones? Should the user's own chats be
able to post into the council inbox (a `/council` command or a chat binding)?
