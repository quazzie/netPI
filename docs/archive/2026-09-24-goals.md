# Goals, steady chat, UI settings (done 2026-09-24)

The user asked for a goal feature ("set the goal and the agent is restarted until the agent disables the goal"),
for tool calls that don't flicker and bump the chat (and a setting to start them collapsed), and for other hardcoded
UI behaviour to become settings. Kept for reference; the tools are in `docs/TOOLS.md` (Goal), the settings in
`docs/SETTINGS.md`, the UI in `docs/UI.md`.

## What other harnesses do (researched 2026-09-24)

- **Codex `/goal`** (v0.128+, `codex-rs/ext/goal`): one goal per thread `{objective ≤4k, status active | paused |
  blocked | usage_limited | budget_limited | complete, token_budget, tokens_used, time_used}`. After every turn an idle
  hook starts a new turn with a continuation prompt (~1k words: persistence, work from evidence, a completion audit
  "that proves completion", blocked only after the same blocker 3 turns running). Model tools: `get_goal`,
  `create_goal` (only when asked), `update_goal(complete | blocked | paused)`. The runtime, not the model, pauses on
  Esc, blocks on errors and after 3 empty or failing turns, and stops at the token budget.
- **Claude Code `/goal`**: a Stop hook where a small model judges the condition after each turn (met / not met /
  impossible); gives up after 8 blocked stops without progress. **ralph-wiggum**: a Stop hook that feeds the same prompt
  back until `<promise>DONE</promise>` or `--max-iterations`.
- **pi `@pi-unipi/ralph`** (installed here): the model calls `ralph_done` to queue the next iteration, prints
  `<promise>COMPLETE</promise>` to finish; a hidden reminder is appended, not put in the system prompt (cache).
- Others: OpenHands (`finish` tool, "continue or finish" auto-replies, stuck detector), Cline/Roo
  (`attempt_completion`, a nudge when no tool is used), Gemini CLI ("Please continue." via a next-speaker check), Qwen
  Code (`/goal` with a verifier that needs tool evidence, 30M token budget, pause after 3 unverifiable turns).
- Pitfalls reported: done too early or with a narrowed scope; the goal lost after compaction; loops that never end
  (confirmation loops, "pause" acknowledged but not done, spinning while waiting for a job); blocking too eagerly on
  one recoverable error.

## Design (as built)

- **State** in the session meta (`meta.goal`, like `meta.todo`; the UI gets it with `session.updated`):
  `{ id, objective, status: active | paused | blocked | complete, reason, tokenBudget, tokensUsed, continuations,
  noProgress, version, createdAt, updatedAt }`. `reason` is why it paused or blocked, or the completion summary.
- **Continuation = a new run**, not an injected turn: a run holds its lane until it ends, so continuing in place would
  keep the lane forever and hit `agent.maxTurns`. `OnRunEndAsync` decides; once the agent is idle the plugin sends a
  `goal` notice (`UserInput.AsNotice`), which starts the next run. Queued user input, a running subagent (its report
  starts a run anyway) or another run starting first all take precedence.
- **Stops enforced by the runtime**:
  - Esc / stop → paused ("stopped");
  - a failed run → paused with the error;
  - `goal.noProgressLimit` (3) continuation runs in a row without a successful tool call (goal tools excluded) → paused;
  - `goal.maxContinuations` (100) → paused;
  - the goal's `tokenBudget`, if set → paused.

  Resume resets the counters.
- **Model tools**: `goal_update { status: complete | blocked | paused, summary }` (paused only when the user asks) and
  `goal_set { objective }` (only when the user explicitly asks for a goal; fails while one is open).
- **Notices** (`kind: "goal"`, appended, never rewritten; the frozen system prompt is untouched):
  - "The user set a goal" or "changed the goal": starts a run when idle; if the agent is busy it arrives at its next
    model call;
  - the continuation: short, with the objective, "work from evidence, check every part before calling it complete,
    blocked only when you need the user";
  - "paused / cleared by the user";
  - re-announced after compaction.

  Each notice carries `{ goalId, version, status }` in its meta, so a hook can tell what the model has already seen.
- **UI**: `/goal <objective>` in the composer (a bare `/goal` opens the editor); a goal strip above the composer with
  the objective, status, continuations and tokens, and Pause / Resume / Edit / Clear. "goal" notices render as rows.
- **RPC**: `goal.get`, `goal.set { sessionId, objective, tokenBudget? }`, `goal.pause`, `goal.resume`, `goal.clear`.
- **Tests**:
  - Agent suite, with the real runner and a scripted model: set → continue → complete; blocked; no-progress pause;
    Esc pauses; a failure pauses; the limit; a user message while active; compaction re-announces.
  - UI mock: the strip and `/goal`.

## Results

- Agent suite: 10 goal tests with the real runner and a scripted model (the loop, every pause, notices, RPC
  validation). Two bugs they caught:
  - numbers in `meta.goal` read back as 0 while the meta was still in memory (`JsonValue.TryGetValue<long>` fails on
    an `int`), so every call re-announced the goal;
  - a run stopped while starting, or failing before its first model call, never reaches the run hooks. The goal stayed
    "active" with nothing running. A watcher on the runs the plugin starts now pauses it, and resume restarts an
    active goal whose agent is idle.
- UI mock: `/goal`, the strip, pause during the first pass (no continuation follows), resume, achieved, dismiss.
- An untitled session started with `/goal` is named after the objective (the host titles from the first user
  message, and there is none).

## Steady chat (tool rows flickering and bumping)

Measured in the mock with every frame recorded (8 quick steps, pinned to the bottom): the chat moved **down** 11 times,
520 px in all:
- −14 px at every step: the streaming block, laid out on its own, was swapped for the finished rows;
- −9 px after every shell command: its live-output preview closed while the "Working…" row appeared;
- −406 px at the end of the run: the steps folding (the old "Collapse finished steps").

Fixes:
- `withStream` lays the streamed answer out as the chat's own items (thinking and tool calls join the open steps
  group, tool rows keep their final key; `StreamingBlock` is gone).
- One fixed working line for the whole run, its height reserved afterwards.
- The shell preview shows only after a second.
- The Steps preference: expanded / fold when done / **folded** (one line per group from the start, showing the latest
  step).

After: no downward move at all, during the run (both modes) or at its end (folded). This is now a check in the UI
mock.

## UI settings (audit of hardcoded behaviour)

- **Added:** chat width (normal / wide / full), zoom (the desktop app remembers the WebView zoom in `window.json`;
  `desktop.zoom`) and spellcheck. "Expand thinking" now also applies while thinking streams.
- **Fixed:**
  - Esc in a title rename or the session search stopped the agent;
  - the composer hints ignored the Ctrl+Enter setting;
  - the settings.json editor never refreshed after an edit elsewhere;
  - a page error when a chat list unmounted.
- **Proposed, not done:**
  - notifications when a run ends in the background (there are none yet);
  - form controls for common settings.json keys (default model, custom instructions, API keys, web search, compaction);
  - new sessions inheriting the current model and effort.

## Later

An independent verifier for "complete" (a subagent that checks against evidence); subagent tokens counted toward the
parent's goal; waking on background jobs instead of relying on the model to wait.
