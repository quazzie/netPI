# Browser use: a browser in the harness, and the user's running browsers

Status: planned · 2026-09-27

## Goal

1. **A browser in the harness.** An agent opens pages, reads them and acts on them (click, type, choose, submit)
   without the user's mouse, keyboard or focus. It works in the headless server too, and several chats can browse at
   once.
2. **The user's running browsers.** With the user's consent, an agent works in the user's own Chrome (their logins and
   cookies): in tabs it opens there, or in a tab the user shares with the chat.

## What we know

From the decisions-lab experiments (`docs/DECISION-MODELS.md`, "Browser use" and "Decisions inside the loop"):

- **The loop works.** The screen is a numbered list of controls (role, name, value, state), the model answers one line
  (`click Save #12`, `type Email #3 = …`, `answer …`, `done`), and a one-turn plan note carries findings between steps.
  qwen3.8-27b at reasoning `low` with the plan passed 16/16 browser tasks (9 on a local test site, 7 on Wikipedia,
  GitHub and the Python docs), with a model step at about 365 ms p50. A done-check and a safety check run as
  decisions on the step's cached head: the safety check blocked 59 of 60 harmful actions at τ 0.3, in 94 ms.
- **Windows UI Automation (UIA) is the wrong layer for a browser.** Most actions need no focus from us (invoke, set
  value, select, expand), but about 10% need real mouse clicks or key presses. Worse, Chrome brings its own window to
  the front when an accessibility action focuses a page element: with Chrome kept behind other windows, it came to the
  front after 42 of 52 steps (decisions-lab `results/cu_web/bg-behind-*`). UIA browsing therefore needs its own visible
  window, and the user must keep off the keyboard and mouse. It stays the tool for native Windows apps.
- **NetPI already drives a browser over the DevTools protocol (CDP).** `HeadlessBrowser` in
  `plugins/NetPI.Tools.Web/ScreenshotTool.cs` launches a headless Edge/Chrome with a throw-away profile, reads its
  port from `DevToolsActivePort`, and talks CDP over a `ClientWebSocket`, with no package.
- **Attaching to the user's Chrome.**
  - Chrome ≥ 136 ignores `--remote-debugging-port` on the default profile ([Chrome blog](https://developer.chrome.com/blog/remote-debugging-port)).
  - Chrome ≥ 144 lets the user allow debugging of the running browser at `chrome://inspect/#remote-debugging`
    ([Chrome blog](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session)). Chrome then asks
    the user to allow each new connection, and shows "Chrome is being controlled by automated test software" while one
    is open.
  - The user runs Chrome 153; Edge 154 is installed.

## Design: one CDP browser layer, three ways to reach a browser

```
browser tool (agent)  ·  browse subagent (local model loop)
            │  snapshot → numbered controls · act by number · screenshot
     BrowserSession (one per chat) ── CDP client (grown from HeadlessBrowser)
            ├─ owned:    a headless Edge/Chrome that NetPI starts, with its own profile
            ├─ attached: the user's Chrome over its DevTools port (Chrome ≥ 144, user allows each connection)
            └─ relayed:  a NetPI extension forwarding CDP through chrome.debugger (fallback, only if needed)
```

Everything above the transport is shared: the same snapshot, actions, safety checks and UI for all three.

### Snapshot

- `Accessibility.getFullAXTree` for each frame (out-of-process iframes through target auto-attach).
- **Kept:**
  - controls: button, link, textbox, combobox, checkbox, radio, tab, menuitem, option, slider, and a named listitem;
  - context: headings and static text;
  - for each, its name, value and states (checked, expanded, selected, disabled, focused).
- **Numbered** `[i]`, each number mapped to its `backendDOMNodeId`.
- **Same text format as the UIA list** (`[button] Save appearance`), so the prompts, the parser, the effect diff and
  the decision checks carry over unchanged.
- **Capped** at about 500 controls, keeping those nearest the viewport (as now).

### Actions (inside the browser: no operating-system input, no focus)

- **click:**
  1. `DOM.scrollIntoViewIfNeeded`;
  2. `DOM.getContentQuads`;
  3. `Input.dispatchMouseEvent` at the element's centre. These are trusted events, like a user's click.
  - Fallback: `Runtime.callFunctionOn` with `this.click()`.
- **type:** `DOM.focus`, select all, then `Input.insertText`. A `<select>` is set through its value, with
  input/change events.
- **key:** `Input.dispatchKeyEvent`. **scroll:** a `mouseWheel` event.
- **navigation and tabs:** `Page.navigate`, history, and `Target.*`.
- **Focus emulation:** `Emulation.setFocusEmulationEnabled`, so a page in the background behaves as if focused.
- **To verify in the spike:** none of this brings an attached, visible Chrome window to the front.

### The `browser` tool (NetPI.Tools.Web, next to `screenshot`, sharing its CDP client)

- **One tool with an `action`:** `open {url}`, `snapshot`, `click {n}`, `type {n, text}`, `key {keys}`,
  `scroll {dir}`, `back`, `tabs`, `screenshot`, `close`. One definition keeps the tool list short, which matters on a
  local model.
- **Content:** the URL, the title, the effect of the last action, then the numbered controls.
- **Details:** `{ url, title, target: 'owned'|'attached', tab, screenshot? }`, documented in `docs/TOOLS.md`.
- **Lifetime:** one `BrowserSession` per chat. It closes with the chat, or after an idle timeout.
- **Treat pages as untrusted:** page text is data, not instructions. The tool result marks it as page content, and the
  tool description says so.

### The owned browser

- **Which browser:** Edge/Chrome from `web.browserPath`, found as for `screenshot`.
- **Headless by default.** `browser.headed` shows a window, so the user can log in by hand or watch.
- **Profile:** a persistent profile under `<home>/browser/<name>` by default, so a login made once stays.
  `browser.profile: "temp"` gives a throw-away profile per chat.
- **One process,** with a tab per chat. `Target.createBrowserContext` can separate chats' cookies when that is wanted.

### Attached: the user's Chrome

- **Connecting:**
  - The user turns on `chrome://inspect/#remote-debugging` once.
  - NetPI finds the port through `DevToolsActivePort` in Chrome's user data folder, which is to be verified; it is
    presumably how `chrome-devtools-mcp --autoConnect` finds it.
  - Chrome asks the user to allow the connection.
- **Scope:**
  - The agent works in tabs it opens, in a window of its own (`Target.createTarget` with a new, background window;
    to verify), and in tabs the user shares with the chat from the Browser tab.
  - Any other target is refused.
- **A CDP method allowlist:** only what the snapshot, the actions and the tab handling need. In particular: no cookie
  or storage readers, no download settings, no `Target.exposeDevToolsProtocol`.
- **Disconnecting:** at the end of the chat, or when the user presses Stop. Nothing is kept.
- **Edge:** the same code, if Edge has the same switch (`edge://inspect`, to verify).

### Relayed: an extension (fallback, only if attaching falls short)

When to build it:
- the switch is missing (a managed Chrome, or Edge);
- the per-connection dialog gets in the way;
- a browser can't be attached at all.

How it works:
- An MV3 extension with the `debugger` permission forwards CDP over a WebSocket to NetPI.
- A pairing token protects the connection; the server already rejects foreign origins.
- Chrome shows its "started debugging this browser" bar while it is connected.

It costs packaging, a host endpoint and upkeep. Decide after phase 3.

### UIA

Not for browsers. It stays in decisions-lab for native Windows apps; a later `computer` tool is idea `idea-xb9rhc`.

## Safety

- **Allowed sites:** a host allowlist per chat or task. Links to other hosts are refused, as in decisions-lab
  `cu_web`.
- **Guardrails:** an `ask:` rule for browser actions on controls named like pay, buy, order, send, publish or delete.
  The decision safety check (τ 0.3) acts as the second opinion before asking.
- **No credentials:** the agent never types into a password field. The user logs in themselves: in the headed owned
  browser, or in their own Chrome.
- **Visible control:** the Browser tab shows what is connected and what the agent does, with Stop always at hand.

## UI: a Browser tab (230–320 px wide)

- **Connections:**
  - Owned: running or idle.
  - My Chrome: off, waiting for your OK, or connected with N tabs.
  - Connect and Disconnect buttons.
- **This chat:**
  - the URL and title;
  - a small screenshot after each step, or a low-rate `Page.startScreencast` while the tab is open;
  - the last actions;
  - Stop.
- **Share a tab:** the user's open tabs (attached), each with a button to share it with this chat.

## Phases

0. **Spike in decisions-lab** (no NetPI change).
   - `cu_cdp.mjs`: the `cu_web` loop over CDP with Node's built-in WebSocket and an owned headless Chrome.
   - Run the same 16 tasks and compare with UIA: pass rate, steps, controls, tokens, time.
   - Then attach to the user's Chrome 153 (after the user turns on the switch) and run 3 local tasks in an agent tab.
     Check the permission dialog and the banner, and that the user's windows, focus and mouse are untouched.
   - The results decide the snapshot format, and whether the extension is needed.
1. **The `browser` tool with the owned browser** (NetPI.Tools.Web).
   - Settings in `docs/SETTINGS.md`, the tool in `docs/TOOLS.md`.
   - Tests in `tests/NetPI.Aux.Tests/WebTests.cs`, against a local test page.
2. **The Browser tab** in the UI.
3. **Attached mode:** connect, share a tab, the method allowlist.
4. **A `browse` subagent.** It runs the browsing loop on the local model (low effort with the plan, the done-check and
   the safety check) and returns the result, so a paid main model doesn't read every page.
5. **The extension relay,** only if phase 3 shows it is needed.

## Open questions

- **Browsers:** Chrome first (it is what runs). Edge too, if its switch exists?
- **The user's tabs:** only tabs the agent opens plus tabs the user shares (recommended), or any open tab?
- **Owned profile:** persistent, so a login made once stays (recommended), or fresh per chat?
- **Tool shape:** one `browser` tool with actions (recommended, shorter tool list), or a tool per action?
